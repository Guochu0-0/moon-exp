# 实验记录规范（v2）

实验结果写成什么样、写到哪里、用什么写，以本技能为准。代码放哪、怎么在服务器上启动和收尾见 `/server` 技能；术语（实验、方法、点亮、Notes 等）见仓库根目录的 `CONTEXT.md`。`workbench/README.md` 只讲工作台界面与读取端。

各产物的字段格式在 [formats.md](formats.md)：目录结构、`exp.toml`、分析、预测、中间结果、TB 日志、训练产物、启动记录、`code/`、`extra/`、扰动变体、评价。写某种产物前，先读它那一节。

## 流程

1. **建目录**：`python -m workbench new E3 --parent E2 [--init E2/main] --title "一句话标题"`。编号取下一个未用的 `E<n>`；用户已在画布上建好的直接用。只研究已有结果、不训练的，建成**分析**（formats.md「分析」）。
2. **跑实验**，代码先提交（见 `/server`）。微调的每个方法写一份 `configs/<方法>.toml`，用 `scripts/finetune/run.py runs/<id>` 跑，它按 formats.md「训练产物」写好全部记录；自己写的训练用 `PredWriter` 写预测，需要时用 `InterWriter` 写中间结果、按「TB 日志」写日志。全部产物放在 `runs/<id>/` 里。
3. **写 Notes**：按下文「Notes 写法」写 `runs/<id>/notes.md`，并做完末尾的自查。
4. **评测与检查**：`python -m workbench eval <id>` 生成 `metrics.json`（分析跳过这一步）；`python -m workbench check` 输出「记录无问题」才算完成。
5. **提交小文件**。大文件由 `.gitignore` 排除，留在 worktree 里；结票时由收尾（`/server`「收尾」）挪到 gpfs 主 checkout 并同步到本地。

## 点亮、方法与 split

- **点亮**是派生状态：任一方法有任一 split 的 `preds/<method>/<split>.jsonl` 即点亮；分析以 `extra/` 下有文件为准。
- 方法按 `preds/<method>/` 自动发现。普通实验只有一个方法，命名为 `main`；基线实验（如 B0）可以挂多个。变体方法命名为 `<方法>__<变体>`（如 `loftr__minmax`）。
- split 为 `train` / `val` / `test`。

## Notes 写法

Notes 是实验唯一的自由文本，写成一篇短论文：Markdown，不加 front matter，UTF-8，LF 换行。agent 起草，用户随后修改；用户改过的文字保持原样，新结果追加在末尾。

篇章结构按 Mensh & Kording《Ten simple rules for structuring papers》（PLOS Comput Biol 2017）。读者是你汇报时的导师：懂研究，但不是这个细分方向的专家，不熟悉所用模型的内部和本项目的细节。只读这篇 Notes，就要能明白为什么做、怎么做、发现了什么、意味着什么。写得通俗，但细节和数字一个不少。

**文风。** 照 [exemplar.md](exemplar.md) 写：苏剑林报告自己补做的一组实验。动笔前先通读一遍，看他怎么交代做了什么、怎么报结果、怎么写意外和没想通的地方、上一句怎么接到下一句，然后用同样的口吻写 Notes。学的是平实、顺着讲下去的写法，不学博客腔（“～”“真让人迷惘”这类）。

**中心结论。** 一篇 Notes 只讲一个中心结论。第一行是一级标题，用一句话说出这个结论，例如 `# 模型依赖的区域解释不了标注点处的误差`。

**只写数据直接支持的话，原因留给讨论会。** 用户看完结果后会和 agent 讨论，再自己定结论；agent 写的 Notes 只为这场讨论提供证据（用户，2026-10-21）。
- 标题、摘要、结果小标题只陈述观察（某设置下某个量是多少、怎样变化），不写原因。
- 数据没有直接检验过的解释不写成结论，也不放进标题和摘要。确有值得提的可能性，在讨论里标明“未检验”，并写出能区分它的检查。
- 不写下一步该做什么实验。

**篇章。** 依次为摘要、引言、方法、结果、讨论，节名是单独成行的粗体（`**摘要**`）。每一层都按语境—内容—结论组织：整篇如此，每节如此，每段也如此。

| 节 | 写什么 |
|---|---|
| 摘要 | 一段讲完整个故事：语境，缺口，做了什么，发现了什么，结论意味着什么 |
| 引言 | 从大到小：研究走到哪一步、看到什么现象；收窄到尚未解决的缺口；最后说本文怎样回答它 |
| 方法 | 读者复核结论所需的设置：模型、数据、样本、每个量的定义和统计检验。按主题分段，段首用斜体小标题（`*模型与数据。*`）。沿用的做法点名出处即可 |
| 结果 | 一串论断，按回答问题的逻辑排列。每段的斜体小标题就是这段的论断（`*依赖区域离标注点的远近与误差无关。*`），正文给出支撑它的数字和图表 |
| 讨论 | 先说缺口被填补到哪一步（哪些问题有了答案、哪些仍没有），再写局限，最后列出尚未解释的现象 |

**流向。** 一个话题讲完再进入下一个。并列的内容用平行的句式，按同一顺序排列。

**术语。** 按导师的知识来写。
- 引言先用白话讲清实验涉及的那段机制（例如模型的某一步怎样从输入算出输出），后文都建立在它之上。
- 每个量在第一次出现处定义，之后全文（包括图注）用同一个名字。用描述性的名字代替符号和代码里的变量名（“最高分位置”而不是 mode）；抽象的量配一个直观的读法（熵读作“相当于平摊在几个位置上”）。
- 每个“差”“误差”都写明和什么比：真值，还是另一种设置的输出。
- 别的实验和本实验的模型都按它们做了什么来称呼。引用论文写论文名或 arXiv 号。
- 次要的核对（例如确认代码重写无误、梯度路径符合预期）在结果里用一段交代结论，不单独设节或配表。

**图表。** 每张图或表支撑一个论断，图和表各自按出现顺序编号。图表放在引用它的段落之后，下一行是说明：`图 1：` 或 `表 1：` 加上它支撑的论断，必要时补一句怎么读。图用相对路径嵌入（`![](extra/concentration.png)`）。

**自查。** 交付前只读标题、摘要和结果的各个小标题，确认它们已经讲出全部发现，并且彼此一致；再确认其中没有一句是数据没检验过的原因。
